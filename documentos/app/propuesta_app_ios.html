1. Objetivo y alcance

Este documento define qué corregirá el lado web, APIs y servidor para que la app iOS (WebView sobre zuitch.com) pueda superar la revisión de Apple. No incluye cambios en DHL ni en el código nativo de iOS, salvo las dependencias explícitas que el equipo iOS debe aportar.

En esta versión de la app iOS las compras digitales se ocultan y bloquean (UI + endpoints) para todos los usuarios de esa sesión iOS, no solo durante la revisión. Las compras de productos físicos y el flujo DHL continúan operando sin intervención.

Apple Login Eliminación de cuenta WebView / cookies Gate compras digitales Checkout físico + DHL Sin tracking iOS Report / block Facebook Login Live / HTTPS

Fuera de alcance

Integración StoreKit / IAP de Apple, cambios en DHL, App Store Connect, certificados nativos, ATT nativo y el binario iOS. Esta propuesta bloquea digitales en WebView; no implementa compras in-app de Apple.

3. Señal de sesión iOS (acuerdo técnico)

Para ocultar/bloquear compras digitales y desactivar tracking hace falta identificar de forma fiable las sesiones que vienen de la app iOS. No basta con ocultar botones: el servidor debe rechazar las operaciones.

Señal acordada (por defecto)

  1. App nativa envía el header X-Zuitch-Client: ios-webview (y/o un User-Agent propio documentado) al llamar a api-v2.php?type=set-browser-cookie.
  2. Servidor valida el access_token, establece la sesión web y marca la sesión con cookie HttpOnly / Secure / SameSite: zuitch_ios_app=1.
  3. UI oculta botones, enlaces y modales de compras digitales cuando el flag está activo.
  4. XHR / API responden con error (p. ej. 403) si se intenta PRO, recarga/transferencia de wallet digital, suscripciones a creadores, anuncios/boosts, créditos de IA o crowdfunding desde esa sesión.
  5. Checkout físico + DHL no se filtran por este flag; siguen disponibles.

4. Compromisos Adrián — web y backend

4.1 — Apple Login en el servidor

  • Validar correctamente la identidad (identity token / JWT de Apple).
  • Crear o vincular cuentas sin solicitar una contraseña adicional.
  • Probar usuarios nuevos y existentes (mismo email o mismo sub Apple).
  • En contexto WebView iOS, no mostrar el modal que obliga a crear password tras login social.
  • Mejorar la vinculación estable por identificador Apple (sub), no solo por email.

4.2 — Eliminación de cuentas

  • Permitir borrar cuentas normales y sociales con verificación segura del titular.
  • No exigir a usuarios de Apple una contraseña que nunca crearon.
  • Eliminar datos y contenido asociados, invalidar sesiones (web y app).
  • Revocar tokens de Apple Login según la referencia de Apple (/auth/revoke) cuando existan credenciales de servicio en servidor.

4.3 — Reportar contenido y bloquear usuarios

  • Dejar visibles y operativos reportes de publicaciones/comentarios y bloqueo de usuarios.
  • Aplicable también a registros sociales (Apple / Facebook).
  • Los reportes deben llegar al administrador; mantener cola de moderación y canal de soporte.
  • Aceptación de términos operativa en registro social.

4.4 — Sesiones y cookies del WebView

  • Revisar y endurecer set-browser-cookie: mantener sesión, evitar bucles de redirección.
  • Limpiar cookies y sesión al cerrar sesión / eliminar cuenta.
  • Proteger cookies (Secure, HttpOnly, SameSite donde aplique).
  • Evitar exponer tokens permanentes en URLs o logs.

4.5 — Compras digitales vs físicas

  • Identificar sesiones iOS (sección 3) y ocultar/bloquear operaciones digitales acordadas.
  • El bloqueo cubre botones, enlaces directos y endpoints — no solo apariencia.
  • Mantener disponibles las compras de productos físicos; DHL no se modifica.

4.6 — Live, APIs y HTTPS

  • Corregir problemas originados en la web, APIs, servidor o servicio de streaming usado por Live.
  • Facilitar usuarios y una transmisión de prueba para reproducir fallos.
  • Garantizar APIs y servicios accesibles con HTTPS válido.
  • La revisión del contenedor WebView nativo queda del lado iOS; los errores de página o streaming, del lado Adrián.

4.7 — Contactos (declaración para Apple)

Qué hace hoy el backend

  • Recibe: un JSON de contactos del teléfono (nombre + número) vía endpoints de sugerencias (p. ej. get-user-suggestions), enviado por la app cuando el usuario concede permiso.
  • Almacena: no se persiste la agenda completa. Se normaliza el teléfono y se hace match contra users.phone_number ya registrados; se devuelven coincidencias no seguidas.
  • Comparte: no se comparte la agenda con terceros. Solo se usa para sugerir usuarios existentes en Zuitch.
  • Finalidad: “encontrar amigos” / sugerencias de seguimiento.
  • Retención: los números del address book no se guardan como tabla de contactos; el match es en tiempo de petición.

Esta declaración se confirma en el documento para que el equipo iOS responda correctamente en App Privacy y en NSContactsUsageDescription. Si el comportamiento cambia, se actualizará esta sección.

4.8 — Sin seguimiento web no autorizado en iOS

  • Identificar píxeles, scripts y cookies de seguimiento (p. ej. Google Analytics inyectado en layout).
  • En contexto iOS (zuitch_ios_app), no inyectar ni ejecutar tracking de terceros.
  • Ajustar el aviso de cookies a lo que realmente se utiliza en ese contexto.
  • Las cookies necesarias para autenticación se mantienen.

4.9 — Facebook Login (backend)

  • Validación del token, creación o vinculación del usuario, generación de sesión.
  • Endpoints, callback y respuestas necesarias para la integración iOS.
  • Entregar endpoints funcionando, accesos y usuarios de prueba.

5. Criterios de aceptación

Checklist verificable (web/backend)

  • Usuario Apple nuevo entra sin crear password adicional.
  • Usuario Apple existente (mismo sub/email) entra y vincula sin password adicional.
  • Eliminación de cuenta social funciona sin pedir password Apple; sesiones invalidadas; revoke Apple ejecutado cuando hay credenciales de servicio.
  • set-browser-cookie deja sesión estable; logout limpia cookies; no hay tokens permanentes en URL o logs.
  • Con flag iOS: UI sin PRO / wallet digital / suscripciones / boosts / AI / crowdfunding; endpoints equivalentes responden error.
  • Con flag iOS: checkout físico y DHL siguen funcionando.
  • Sin GA ni scripts de tracking en páginas servidas a sesión iOS.
  • Reportar post/comentario, bloquear usuario y términos visibles/operativos tras login social.
  • Facebook Login: flujo documentado + usuarios de prueba operativos.
  • Live: al menos un usuario y una transmisión de prueba accesibles por HTTPS.
  • Declaración de contactos coherente con el comportamiento real del servidor.

7. Dependencias del equipo iOS

Para que el lado web cumpla los criterios de aceptación, el equipo iOS debe aportar lo siguiente.

  1. Señal de cliente: enviar X-Zuitch-Client: ios-webview (o UA acordado) en la llamada a set-browser-cookie y en navegación WebView si se acuerda.
  2. Sign in with Apple nativo: obtener identity token y enviarlo al endpoint social-login (provider=apple (el backend valida; la UI nativa es responsabilidad iOS).
  3. Credenciales Apple para revoke (si aún no están en servidor): Team ID, Key ID, Services ID, archivo .p8 por canal seguro — necesarias para revocación al borrar cuenta.
  4. Pruebas en dispositivo: verificar WebView, cookies, login, delete, gate de compras y Live en iPhone/TestFlight.
  5. App Privacy / ATT: etiquetas de privacidad y permiso de tracking nativo según lo declarado (contactos match-only; sin tracking web en iOS).
  6. Facebook: App ID/secret vigentes y, si aplica, usuarios de prueba en Meta; el backend los consume.

IAP / StoreKit

Esta versión no vende digitales dentro de iOS: se bloquean. Si en el futuro se habilitan compras digitales, haría falta un proyecto aparte con StoreKit e IAP — fuera de este documento.
