4. Música y audio — única opción: worker YouTube

Para reels queda una sola propuesta de música: un servidor extra (worker) consume la API de YouTube para buscar, descarga el audio, lo convierte/limpia y lo entrega a Zuitch. En el editor el usuario solo ve “buscar canción” y la pista lista para recortar y mezclar. No se cotizan Epidemic, biblioteca admin como catálogo principal ni embed como sustituto de la pista del reel.

Flujo (cómo funciona)

1. Usuario en Zuitch (editor de reels) Escribe la canción o pega un enlace. Zuitch no habla directo con YouTube.
↓
2. Backend Zuitch Pide al worker: buscar o preparar audio. Si la pista ya está en cache, la reutiliza.
↓
3. Servidor worker (IP distinta) Usa la API / extracción desde su IP: busca resultados y descarga el audio.
↓
4. Conversión en el worker FFmpeg → solo audio (MP3/M4A), sin metadatos de origen. Devuelve el archivo a Zuitch.
↓
5. Zuitch guarda y mezcla La pista queda en la plataforma; el usuario recorta/volúmenes; al publicar FFmpeg la pega al reel.
↓
Riesgo operativo Cada cierto tiempo YouTube puede inhabilitar el acceso (API / IP / anti-bot) en ese servidor. Hay que conseguir un VPS o IP nueva (o rotar al de respaldo) y volver a apuntar el worker. Ver §11.

5. Copyright — escaneo, muteo y portal de reclamos

Incluido en la fase 1. Es la pieza para que, cuando haga falta, un titular pueda reclamar y el audio del reel se enmudezca sin borrar el video.

  1. Escaneo al publicar

    Al publicar, el audio se consulta en un servicio externo de reconocimiento (cuenta y consumo los paga Zuitch). Si hay coincidencia y la pista no está en el catálogo permitido, el reel se publica enmudecido y queda registro. Lo que no esté en la base del proveedor no se detecta.

  2. Portal de reclamos

    Un titular envía el reclamo con el enlace del reel (y datos de contacto / prueba de titularidad según el formulario). El administrador revisa, enmudece o restaura el audio, el autor puede apelar una vez y el administrador cierra. No reparte regalías ni sustituye un abogado: es cola de revisión dentro del sitio.

Cómo encaja con el worker

El audio llega desde el worker a Zuitch; el usuario lo elige y publica (como en el demo). Si hay un reclamo válido o el escaneo marca la pista, el reel puede quedar visible con audio en silencio. El portal no evita bloqueos de API/IP en el worker (§4 / §11).

Acción Quién Efecto
Publicar reel Usuario Escaneo automático → OK o muteo preventivo
Abrir reclamo Titular / tercero Ticket con enlace al reel
Enmudecer / restaurar Admin Audio off/on sin borrar el video
Apelar Autor del reel Una apelación; admin cierra

6. Fase 1 — Módulo Reels

Encima del editor en línea. La música entra solo por el worker YouTube (§4): buscar → descargar en el servidor extra → pasar audio a Zuitch → mezclar. Copyright completa el módulo. Además: home de inicio tipo reels y contador de likes totales en el perfil. Letras y filtros quedan fuera de esta propuesta (se cotizan aparte si se piden).

Cómo funciona el audio en el reel

  1. El usuario busca en el editor; Zuitch pide al worker; el worker usa la API/descarga desde su IP.

  2. El audio limpio queda en Zuitch (cache). Se puede reutilizar (“Usar este sonido”) sin volver a bajar.

  3. Al publicar, FFmpeg mezcla la pista en el MP4 del reel (recorte y volúmenes del editor).

Entregables (fase 1)

  1. Música / Worker YouTube

    UI de búsqueda, integración Zuitch↔worker, descarga/conversión, cache de pistas, reutilizar audio ya bajado y mezcla al publicar. Subir MP3 propio se mantiene como respaldo.

  2. Copyright / Escaneo, muteo y portal de reclamos

    Ver §5. Un solo paquete: detección al publicar + cola admin de reclamos con muteo/restauración.

  3. Home de inicio tipo reels

    La pantalla de inicio del sitio abre en un feed vertical tipo reels (scroll de videos a pantalla completa), en la línea del producto actual, como puerta de entrada principal.

  4. Contador de likes totales en el perfil

    En el perfil de cada usuario se muestra cuántos likes totales ha recibido (suma de likes de sus reels / contenidos aplicables). Visible para el visitante del perfil.

Riesgo del worker

YouTube puede inhabilitar de tanto en tanto el acceso (API o IP) en el servidor worker. Mitigación operativa: otro VPS/IP y rotación (§11). Eso es operación de infra, no un bug del editor.

Todo lo relacionado con Payphone queda aquí: recarga de billetera, tokenización y split en el checkout.

Recarga de billetera

Un botón más en la recarga de saldo web. Se crea el cobro, Payphone confirma en el servidor y recién ahí se suma el saldo. Plan Pro, anuncios y checkout de tienda pueden seguir con billetera según se defina al arrancar. App Android no entra. Se entrega un texto corto de cómo queda integrada la pasarela. El trámite lo hace Zuitch.

Tokenización

Guardar identificador de tarjeta para la siguiente recarga (Visa/Mastercard). No es débito automático. Condiciones comerciales de Payphone (retenciones / reversos) aplican según su documentación vigente al momento de integrar.

Split en el checkout

Pedido de tienda con Payphone repartido entre vendedor y comisión Zuitch. Comisión de tarjeta fuera del reparto, según tarifas vigentes. Modo inmediato en esta entrega (sin reverso automático), salvo que al cotizar la fase 2 se acuerde otra cosa.

Fuera de esta fase

Programa Partners de Payphone (descontinuado / no activo): no se cotiza ni se asume como requisito. App Android y trámites legales ante Payphone siguen a cargo de Zuitch.

11. Servidor worker YouTube

Para que la búsqueda y la descarga de audio no salgan por la IP de zuitch.com, se necesita un servidor VPS adicional con otra IP (worker). Ese servidor consume la API / obtiene el audio, lo convierte (FFmpeg), limpia metadatos y lo entrega a Zuitch. El hosting de ese VPS lo contrata y paga Zuitch directamente al proveedor; no se suma un monto extra en esta cotización.

Para qué sirve

  • Salir a YouTube desde una IP distinta a la del sitio.
  • Buscar, descargar y convertir el audio antes de pasarlo a Zuitch.
  • Si YouTube inhabilita el acceso en esa IP, se puede montar otro VPS/IP y volver a conectar el worker.

Cómo funciona si bloquean la IP

  1. El worker falla (403 / timeout / anti-bot o API inhabilitada).

  2. Se marca esa IP como caída.

  3. Se apunta Zuitch a un VPS/IP nuevo (o de respaldo) y se reintenta.

Riesgo principal

Cada cierto tiempo YouTube puede inhabilitar el API o la IP del servidor worker. En ese caso hay que conseguir un servidor/IP nuevo y volver a conectar Zuitch. Eso es mantenimiento operativo a cargo de Zuitch. El portal de reclamos (§5) cubre muteo por copyright; no evita el bloqueo del worker.
