Plan de seguridad

1. Objetivo

Proteger la plataforma social WoWonder de Zuitch en capas: filtrar tráfico malicioso antes de que llegue al servidor, reforzar formularios y endpoints públicos contra automatismos, y versionar el código de forma segura y trazable.

Este documento define qué se propone, qué debe preparar el cliente en servicios externos (cuentas, DNS, claves) y qué implementará el equipo técnico una vez recibidos esos datos por un canal seguro. No incluye secretos reales: solo placeholders y pasos.

Resumen orientativo del entorno actual (Plesk + nginx + PHP-FPM + Node livestream). Sin listar rutas o archivos sensibles en detalle.

3. Arquitectura propuesta

El usuario o bot pasa primero por Cloudflare. Solo el tráfico permitido llega a nginx/Plesk y a la aplicación. reCAPTCHA actúa en formularios humanos; Git versiona el código sin secretos.

Principio

reCAPTCHA no sustituye un WAF. Cloudflare no sustituye buenas prácticas de código ni Git. Las tres capas se complementan: edge (Cloudflare), aplicación (reCAPTCHA + hardening) y proceso (Git).

4. Fase A — Cloudflare (anti-bots en el edge)

Proxy naranja delante de zuitch.com (y subdominios acordados) para ocultar la IP de origen, aplicar WAF, Bot Fight y límites de tasa en rutas sensibles.

A.1 — Lo que debe hacer el cliente (paso a paso)

  1. Crear cuenta en Cloudflare (correo corporativo recomendado).
  2. Añadir el sitio: dominio zuitch.com. Incluir también live.zuitch.com (u otros subdominios críticos) si el tráfico livestream/API pasa por ellos.
  3. Revisar el inventario DNS que Cloudflare importa (A, CNAME, MX, TXT). Confirmar que correo y registros existentes no se pierden antes de cambiar nameservers.
  4. Cambiar nameservers en el registrador del dominio a los que indique Cloudflare (ejemplo orientativo: xxx.ns.cloudflare.com). Propagación: minutos a 48 h.
  5. Esperar estado Active en el dashboard (zona activa y SSL en proceso).
  6. Activar proxy naranja en los registros A/CNAME web (nube naranja = tráfico vía Cloudflare). No poner en naranja registros que deban ir directo al origen sin proxy (p. ej. algunos MX/servicios mail si aplica).
  7. Copiar y enviar por canal seguro (no en este HTML ni en chat público):
    • Zone ID de la zona zuitch.com.
    • API Token con permisos mínimos: Zone DNS Edit, WAF, Firewall, Cache Purge (sin permisos globales innecesarios).
    • Confirmación de que el proxy naranja está activo en los hosts web.
    • Lista de subdominios que deben quedar protegidos.

Plantilla de entrega (placeholders)

  • Zone ID: ________________
  • API Token: ________________ (enviar solo por canal seguro)
  • Dominios/subdominios: zuitch.com, www, live, otros: ________
  • Ventana de mantenimiento DNS acordada: ____ / ____

A.2 — Lo que implementará el equipo técnico

  • SSL/TLS en modo Full (Strict) con certificado válido en el origen.
  • Bot Fight Mode / Super Bot Fight (según plan) para mitigar scrapers y automatismos.
  • WAF managed rules + reglas personalizadas para admin, login y APIs.
  • Rate limiting en rutas sensibles: /requests.php, /api*, login/registro, recuperación de contraseña.
  • Challenge (JS/Managed) en rutas de alto riesgo; exclusión cuidadosa de callbacks móviles/API legítimos.
  • Ocultación de la IP de origen; revisión de que el servidor solo acepte tráfico esperado vía Cloudflare (cuando sea viable).

5. Fase B — Google reCAPTCHA

La plataforma ya contempla reCAPTCHA (Admin → General Settings). Se recomienda reCAPTCHA v2 “No soy un robot” por compatibilidad con el flujo actual de WoWonder. Las claves deben estar vigentes y asociadas a los dominios correctos.

B.1 — Lo que debe hacer el cliente (paso a paso)

  1. Entrar a Google reCAPTCHA Admin con una cuenta Google del proyecto.
  2. Crear o verificar un sitio tipo reCAPTCHA v2 → “I’m not a robot” Checkbox.
  3. En dominios autorizados, añadir al menos: zuitch.com y www.zuitch.com (y cualquier host de prueba que se use).
  4. Copiar Site Key y Secret Key.
  5. Entregar ambas claves por canal seguro al equipo técnico (no pegarlas en este documento público).

Plantilla de entrega (placeholders)

  • Site Key: ________________
  • Secret Key: ________________ (solo canal seguro)
  • Tipo: reCAPTCHA v2 Checkbox
  • Dominios registrados: zuitch.com, www.zuitch.com, otros: ________

B.2 — Lo que implementará el equipo técnico

  • Activar/verificar reCAPTCHA en Admin y guardar Site Key + Secret Key.
  • Comprobar widgets en registro, contacto, forgot-password y creación de blogs.
  • Valorar ampliar verificación a login y a endpoints públicos abusables si el tráfico lo justifica.
  • Probar que usuarios reales pasan y que envíos sin token fallan.

6. Fase C — Git y versionamiento

Ya existe repositorio Git con remoto en GitHub (AlfaBusines2025/zuitch.com). El objetivo es un proceso claro: cada cambio trazable, sin secretos ni dumps en el historial, y deploy controlado en Plesk.

C.1 — Lo que debe hacer el cliente (paso a paso)

  1. Confirmar acceso de lectura/escritura al repositorio GitHub del proyecto (invitar al desarrollador como colaborador si aún no lo es).
  2. Acordar política de ramas: master (o main) estable + ramas feature/… o develop.
  3. Comprometerse a no subir nunca: config.php, .env, dumps *.sql, zips de backup, carpetas upload/ con media de usuarios.
  4. Definir quién aprueba merges a la rama de producción (dueño del producto / técnico).

Plantilla de entrega

  • URL del repo: https://github.com/…/…
  • Usuario(s) GitHub invitados: ________________
  • Rama de producción acordada: master / ________

C.2 — Lo que implementará el equipo técnico

  • Reforzar .gitignore (config, SQL, zips, uploads, caché, logs, vendor/node_modules).
  • Revisar que no haya secretos en commits recientes; plan de remediación si aparecen.
  • Convención de commits y flujo: branch → cambios → (PR opcional) → merge → deploy en Plesk.
  • Checklist pre-deploy (backup DB, sin archivos basura en webroot, prueba smoke).
  • GitHub Actions solo para checks (lint/smoke) si se acuerda; sin deploy automático salvo acuerdo explícito.

C.3 — Cómo pedir un cambio versionado (operativa)

  1. Abrir rama desde la rama estable.
  2. Implementar y probar en entorno/staging o ventana controlada.
  3. Commit con mensaje claro (por qué del cambio).
  4. Merge a la rama de producción tras revisión.
  5. Desplegar en Plesk y verificar login, home y un formulario clave.

7. Fase D — Hardening servidor y aplicación

Trabajo principalmente técnico una vez Cloudflare y claves estén disponibles. Reduce la superficie de ataque en el origen.

  • Retirar o bloquear por HTTP archivos sensibles del webroot (backups, SQL, zips de instalación).
  • Añadir headers: X-Frame-Options, X-Content-Type-Options, CSP progresiva (sin romper el frontend de golpe).
  • Revisar reglas que desactivan escaneo de POST; reactivar o sustituir con controles equivalentes si es viable.
  • Revisar límites de login fallidos y permisos de carpetas de subida (upload/).
  • Restringir exposición de admin-cp, APIs y Node livestream apoyándose en reglas Cloudflare.
  • Roadmap PHP 7.4 → 8.2/8.3: fase posterior (alto impacto en WoWonder; requiere pruebas amplias; no bloquea el resto).

9. Orden recomendado de ejecución

  1. Backup + Git limpio Copia de seguridad de archivos/BD; asegurar que secretos no entren al repo.
  2. reCAPTCHA keys Crear/verificar claves y entregarlas; activación rápida en Admin con bajo riesgo de downtime.
  3. Cloudflare DNS Cambio de nameservers en ventana acordada; validar sitio, correo y SSL.
  4. WAF / bots / rate limit Activar protecciones; ajustar excepciones para app móvil y APIs legítimas.
  5. Headers y webroot Endurecer respuestas HTTP y eliminar exposición de artefactos sensibles.
  6. Revisión login / API Probar abusos básicos, formularios y endpoints AJAX críticos.
  7. Roadmap PHP Planificar migración 8.x como fase independiente con batería de pruebas.

10. Riesgos y notas

  • Cambio de nameservers: puede haber minutos de inconsistencia DNS; coordinar ventana y no tocar MX a la ligera.
  • Bot Fight / Challenges: posibles falsos positivos en apps nativas, webviews o clientes API; requieren allowlist/excepciones.
  • reCAPTCHA: reduce spam en formularios; no sustituye WAF ni rate limit en APIs.
  • Git: versiona código; no es backup de media en upload/ ni de la base de datos.
  • PHP 7.4 EOL: riesgo de seguridad creciente; se documenta como fase posterior por impacto en WoWonder.
  • Secretos: Zone ID, API Token, Site Key y Secret Key nunca deben publicarse en este HTML ni en el repo.

Canal seguro para claves

Entregar tokens y secret keys por un medio cifrado o privado acordado (gestor de secretos, mensaje cifrado, panel seguro). No usar correo sin cifrar ni issues públicos de GitHub.
